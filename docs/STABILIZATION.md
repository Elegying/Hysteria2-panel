# v0.34 稳定化策略

本项目进入稳定化窗口。目标不是继续扩展功能，而是把现有单机与多节点能力变成可重复验证、可观测、可安全发布的基线。

## 合并范围

稳定化窗口只接受以下变更：P0–P2 缺陷修复、安全修复、兼容性修复、测试去抖、可观测性、文档和不改变行为的模块拆分。新入口、新持久化身份、新外部依赖、新协议字段或需要迁移用户配置的功能，默认推迟到下一个功能版本；确需提前时必须增加 ADR、迁移/回滚方案和对应 E2E。

## 必过门禁

- Python 3.8、3.12、3.13 全套单元与集成测试；Python 3.13 负责捕获 SQLite `ResourceWarning` 回归。
- Ruff、Bandit、ShellCheck、安装器语法、空白与历史隐私检查。
- 两节点控制 E2E：中央故障时 spool 持久化，另一节点继续结算，恢复后精确重放且无重复累计。
- 真实 Chrome 桌面 1380×900 与手机 375×812 渲染 smoke；界面结构测试覆盖标签、对话框、Esc 和焦点回归。
- systemd 服务语义、防火墙集成、完整安装 E2E，以及 Ubuntu、Debian、Rocky Linux 的 amd64/arm64 安装矩阵。
- 标签发布必须绑定精确提交，并等待 `test (3.13)` 与 `browser-smoke` 等全部正式门禁后才签名公开。

## 发布判定

候选版本至少连续 48 小时没有新增 P0/P1，所有必过门禁在同一候选提交上为绿色，且 canary 节点完成一次中央重启、一次网络中断重放和一次 `max-unavailable=1` 回滚演练。截图不是 WCAG 合规证明；发布前仍需在真实浏览器完成键盘路径、200% 缩放和屏幕阅读器抽查。

## 回归处理

出现失败先保留日志、SQLite/WAL 状态、spool 和安装事务标记，不通过重复执行或手工删除来“变绿”。确认属于测试环境抖动时，必须先增加可复现证据和有界超时解释，再调整门禁。生产滚动升级中任一节点的健康、身份、流量或真实 Hysteria 握手失败，立即停止后续节点并按 `docs/DEPLOYMENT.md` 回滚。
