# Hysteria2-panel v0.13.0 生产级审查报告

审查日期：2026-08-12（Asia/Shanghai）

## 结论

本轮在“已发放节点身份不可变化”的前提下完成代码、部署、运行、保活、用户管理、迁移恢复、安全和 UI 审查。代码与本地浏览器质量门达到发布候选标准；未修改用户 URI 的域名、UDP 端口、认证 token、HMAC、TLS 证书、私钥或 `pinSHA256`，也未切换到 Brutal。

审查发现并修复 3 个高风险可靠性缺口、1 个中风险保活缺口和 1 个大用户量性能问题。115 项自动化测试、Python/shell 语法、ShellCheck、Ruff、Bandit 和补丁格式检查全部通过。真实云主机重装、DNS 切换、Hysteria 握手、YouTube 长时间播放和跨运营商丢包仍属于发布后的网络验收，不能由本地测试冒充。

## 审查范围与方法

- 代码：认证、SQLite、token 派生、备份 ZIP、恢复事务、HTTP 安全、在线更新和错误路径。
- 部署：全新安装、重复部署、在线升级、依赖检测、架构选择、校验和、systemd、sudoers、sysctl、健康检查和失败回滚。
- 运行：面板、回环认证、流量采集、Hysteria、TCP 探测和 systemd 生命周期。
- 用户：新增、禁用、删除、轮换、分享、设备限制、流量限额、统计和批量重置。
- 界面：1440×900 桌面和 375×812 手机浏览器，356 用户列表、搜索、添加/迁移弹窗和登录布局。
- 迁移：多用户新式 token、旧式不可逆 token、HMAC、证书/私钥、指纹、用户限制、流量和失败回滚。

## 已修复问题

| 严重度 | 问题 | 修复结果 |
|---|---|---|
| 高 | 恢复仅在写入前校验；磁盘最终状态被静默改坏时仍可能报告成功 | 写入后从最终路径逐列比较全部代理用户行，并验证 SQLite、全部可恢复 token、HMAC、证书/私钥配对、指纹、有效期和用户数；失败纳入原事务回滚 |
| 高 | 恢复失败后 `pending-restore.zip` 一直存在，会阻塞后续所有上传 | 失败 ZIP 改名隔离、权限固定为 `0600`，保留取证材料并立即释放队列 |
| 高 | 升级会备份但最终健康检查失败时不会自动恢复 | 现有安装写入后一直保持回滚保护；任一步失败时恢复程序、配置、TLS 身份、数据库、unit、sudoers 和网络参数并重启旧服务 |
| 中 | 面板 HTTP 或流量采集线程退出后，认证主线程仍运行，systemd 可能继续显示 active | 三个长期 worker 统一监督；任一异常退出会关闭本地服务并令进程失败，由 `Restart=on-failure` 接管 |
| 中 | 356 用户页面未压缩，传输接近 0.75 MB；连续输入每次都同步遍历全部行 | gzip 协商、动画帧合并搜索、粘附表头、稳定滚动条、数字等宽和减少动态效果偏好 |
| 低 | 迁移文档先切 DNS 后恢复，可能把旧用户流量提前送到未恢复身份的新主机 | 改为先通过新服务器 IP 恢复并验证，随后才切 DNS，并保留旧服务器一个 TTL 回退窗口 |
| 低 | 升级备份目录只有秒级时间戳，极端并发可能复用目录 | 增加随机后缀；下载增加固定总超时，避免网络请求无限阻塞 |

## 已发放节点的连续性证明

旧链接继续可用需要同时保持下列字段：

| 身份字段 | 备份/恢复行为 | 变化后后果 |
|---|---|---|
| 域名或旧 URI 中的 IP | 清单记录；恢复要求域名一致 | 旧客户端仍访问旧地址，无法无感迁移 |
| UDP 端口 | 清单记录；恢复要求端口一致 | 旧客户端连接错误端口 |
| 用户 token | 代理用户行整体恢复；新式 token 由原 seed + 原 HMAC 重建 | Hysteria HTTP auth 拒绝旧用户 |
| HMAC key | ZIP 保存并恢复到环境文件 | 新式用户生成的 token 与指纹不一致 |
| TLS 证书与私钥 | 两者原样保存、校验配对并恢复 | 服务端无法证明原 TLS 身份 |
| `pinSHA256` | 从原证书重算并与清单、环境文件交叉验证 | 固定指纹客户端拒绝握手 |

回归测试覆盖多个新式用户和一个旧式不可逆 token 用户：恢复后所有旧 token 均继续认证；新式用户重新生成的 URI 逐字节一致；旧式 token 虽不能从数据库重新显示，但原已发放链接仍然有效；设备限制、累计流量、证书和私钥字节均保持不变。

迁移必须按以下顺序执行：

1. 旧服务器保持在线，生成并离线保存最新 ZIP；
2. 新服务器使用完全相同的 `PUBLIC_HOST`、Hysteria UDP 端口和出站策略部署；
3. 放行新主机端口，通过新服务器 IP 登录面板，上传恢复；
4. 核对用户数、证书指纹、面板/认证/Hysteria/TCP 探测状态；
5. 再切换 DNS，并用已经发放的旧链接测试 Hysteria 握手、HTTP `204`、网页和 YouTube；
6. 保留旧服务器至少一个 DNS TTL，稳定后再下线。

如果旧 URI 直接使用旧 IP，或更换 UDP 端口、用户 token、证书/私钥，无法做到无感迁移。10 年证书到期或主动重签后指纹必然变化，届时必须重新分享链接；在此之前普通升级、重装和按上述流程恢复不会主动换证书。

## 连接体验与稳定性

- 固定官方 Hysteria 2.12.1 二进制和 amd64/arm64 SHA-256；该版本包含空闲/睡眠后重连改进。
- Hysteria 隧道继续使用 `bbr` + `standard`，并忽略客户端带宽上报；不使用依赖准确带宽估算的 Brutal，避免多人共用线路时争抢和抖动。
- UDP 收发缓冲至少 16 MiB，Hysteria 进程 `Nice=-5`、`LimitNOFILE=1048576`；内核支持时为服务器到 YouTube/CDN/网页源站的 TCP 出站启用 `fq` + BBR。
- 默认 `web` ACL 允许 DNS、NTP、HTTP、HTTPS 和 HTTP/3（UDP 443），拒绝私网和其他端口。它能阻断常规 BT/PT、DHT 和 uTP，但不是 DPI，无法保证识别伪装在 80/443 上的加密 P2P。
- TCP 19999 只用于客户端延迟探测；真实 Hysteria 可用性必须用 UDP/QUIC 握手和代理后的 HTTP/视频流量判断。ICMP `ping` 不经过 Hysteria。

本轮没有加入端口跳跃、激进 QUIC 参数或更多“万能 sysctl”。这些改动缺乏当前线路数据，可能破坏稳定性，且不属于保持旧链接不变的安全范围。

## 程序保活与故障行为

| 组件 | 监听/职责 | 保活与失败语义 |
|---|---|---|
| 面板进程 | 公网 TCP 19998 + 回环认证 19996 + 流量采集 | 内部 worker 统一监督；异常使进程失败；systemd `Restart=on-failure` |
| Hysteria | 公网 UDP 19999 | 独立非 root 用户、沙箱、`Restart=on-failure`；依赖面板认证 |
| TCP 探测 | 公网 TCP 19999 | `BindsTo`/`PartOf` Hysteria，随主服务启停并独立重启 |
| 恢复任务 | root oneshot | 停止冲突服务、双重校验、自动备份/回滚，结束后重新拉起全部服务 |
| 更新任务 | root oneshot | 固定 GitHub 正式版本、固定安装器路径和非交互参数；安装器承担健康检查与自动回滚 |

认证或统计后端不可确认状态时采用失败关闭：新连接被拒绝，不会为了“看起来在线”而绕过设备或流量限制。系统恢复后客户端可按自身重连策略重新认证。

## 用户管理审查

- 用户名有唯一性、长度和控制字符校验；HTML 输出转义，写操作要求会话和 CSRF。
- 默认最多 3 个同时在线的 Hysteria 客户端实例。已有 3 个实例不受影响，第 4 个认证失败；5 秒短期预留防止并发认证同时越限。
- “设备”不是硬件指纹。同一网关后的多台设备可能算一个实例，同一设备运行多个核心也可能算多个实例。
- 默认总流量 250 GiB；达到配额后拒绝新认证并持续清退仍在线实例。统计不可用时不伪造流量或在线状态。
- 禁用、删除、轮换和超额会调用固定统计 API 清退连接；新 token 不以明文存储。
- 管理员第 5 次错误登录立即按来源 IP 锁定 15 分钟；未知账号执行等价密码校验，记录数量有界。

## 部署与安全评价

- 支持合同：Debian/Ubuntu `apt`，RHEL/Rocky/Alma/CentOS Stream/Fedora `dnf`/`yum`，systemd，Python 3.8+，Linux amd64/arm64。
- 安装器拒绝覆盖非本项目管理的同名路径；下载 Hysteria、面板和探测程序后校验固定 SHA-256，并做 Python/shell 语法检查。
- 认证和统计只监听回环；Hysteria、探测、恢复和更新 unit 使用最小权限与 systemd 沙箱；面板 sudoers 只允许固定服务动作。
- 在线更新不接受浏览器提供版本、URL 或命令，只接受固定仓库的严格 `vX.Y.Z` 正式版本。
- 默认 HTTP 是明确的产品选择，但管理员密码、会话和备份 ZIP 会明文经过网络。登录锁定、CSRF、CSP 和 Cookie 属性不能阻止同链路窃听；生产上必须把 TCP 19998 限制到可信管理 IP，或通过 SSH/VPN 管理。
- 备份 ZIP 等同于全部用户凭据和 TLS 私钥，目前未做口令加密；必须离线、加密存储并限制副本。

## 残余风险与下一步

1. **HTTP 管理面风险（高，运维控制）**：立即在云安全组/主机防火墙限制 TCP 19998 来源；不要在不可信网络直接下载或上传迁移 ZIP。
2. **多服务器一致性（高，架构限制）**：相同域名多 A/AAAA、相同端口、相同备份身份可让旧链接连接任一服务器，但每台 SQLite 的在线数、设备限制、流量和禁用状态彼此独立。需要真正的全局配额和实时用户管理时，应下一阶段引入中心认证/计量服务，不能把 DNS 轮询误认为状态一致的负载均衡。
3. **证书到期（中，计划风险）**：为 10 年证书增加到期前 180/90/30 天外部告警；到期重签必须安排重新分享窗口。
4. **备份保密（中）**：下一阶段可增加客户端侧或离线口令加密，但不能破坏当前 v1 ZIP 的可恢复性；实施前需要兼容策略和恢复演练。
5. **真实网络验证（中）**：在一台非关键服务器先升级，执行旧链接握手、HTTP `204`、YouTube 30 分钟、休眠唤醒、丢包环境和 systemd 重启测试，再分批推广。
6. **单文件维护成本（低）**：当前单文件、零依赖显著降低部署风险，本轮不做大拆分。后续若功能继续增长，应先建立稳定内部接口和迁移测试，再分离存储、HTTP 与运维模块。

综合判断：v0.13.0 可以进入受控发布和单机试运行；不得把本地自动化结果表述为已经完成真实跨境网络或所有 Linux 发行版实机认证。
