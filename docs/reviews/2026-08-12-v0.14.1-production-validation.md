# Hysteria2-panel v0.14.1 生产升级与线路验证报告

> 公开版本已把实际生产域名和 IP 替换为 `example.com` 与 RFC 5737 文档地址；测试结论和相对节点编号保持不变。

验证日期：2026-08-12（Asia/Shanghai）

## 结论

在线更新失效已经定位、修复并通过真实旧版本升级链验证。正式发布版为 `v0.14.1`，`203.0.113.10`、`203.0.113.11` 和用于回归验证的 `203.0.113.20` 均已从 `v0.12.2` 升级至 `v0.14.1`。

升级前后两台目标服务器均保留 339 个用户，现有节点域名、UDP 端口、用户认证身份、HMAC、TLS 证书/私钥和证书指纹未改变。使用既有用户身份与原证书指纹，分别与两台服务器完成真实 Hysteria 2 UDP/QUIC 握手，并通过代理访问 Google 204、YouTube 首页和 Cloudflare 10 MiB 下载。因此本轮升级没有使已发放链接失效。

## 在线更新根因与修复

旧版更新单元把 `RestrictAddressFamilies` 限定为 `AF_INET AF_INET6 AF_UNIX`，而安装器的 IPv4 自动探测使用 `ip addr`，该命令需要 `AF_NETLINK`。在 `set -e` 下，探测失败会令旧更新任务在第 315 行直接退出，所以界面能够检查到新版，但点击安装后版本不变且没有可靠的失败反馈。

`v0.14.1` 同时处理新旧两条路径：

- 非关键网卡自动探测失败时安全降级，不再阻断已安装系统升级；
- 新写入的更新 unit 明确允许 `AF_NETLINK`，后续升级不再触发该限制；
- 更新状态持久化到 `/var/lib/hysteria2-panel/update-status.json`，前端轮询排队、运行、成功或失败状态；
- 只有 systemd 更新任务成功结束且当前版本不低于目标版本时才显示成功；
- 更新失败、状态损坏、任务结束但版本未改变都会给出明确错误，而不是“点击无反应”。

在仍运行 `v0.12.2` 的 `203.0.113.20` 上执行兼容升级：旧 unit 的网卡探测警告被安全降级，任务最终返回更新成功；版本变为 `v0.14.1`，面板、Hysteria 和 TCP 探测三项服务均 active，339 个用户和原证书指纹不变。安装器随后写入包含 `AF_NETLINK` 的新 unit，完成未来更新路径修复。

## 新增运维与用户管理能力

- 用户列表在实时在线客户端实例数高于该用户限制时，将用户名标红并显示超限提示。
- “添加用户”旁增加“编辑用户”入口，可在弹窗中修改单个用户的设备限制和总流量额度。
- 编辑使用 `generation` 乐观锁，且只更新限额；不会修改用户名、token seed、HMAC、证书指纹或累计流量，已发放节点链接保持不变。
- 系统资源模块右上角增加“重启服务器”按钮，操作前明确二次确认；后端要求管理员会话和 CSRF，写入审计后仅执行固定的非阻塞 systemd reboot 命令。
- 重启前尽力把待采集流量持久化。systemd 会在服务器重新启动后自动拉起面板、Hysteria 和 TCP 探测。

本次验证没有点击两台生产服务器的重启按钮，避免无业务必要的在线中断；按钮、后端固定命令、权限边界和失败路径由自动化测试覆盖。

## 设备限制的真实语义

Hysteria 官方 Traffic Stats API 的 `/online` 返回的是每个认证用户名的客户端实例数量，不提供硬件设备指纹。当前默认限制 3 个实例：已有 3 个实例继续工作，第 4 次新认证被拒绝，不会踢掉前 3 个；短期 pending 预留用于避免并发认证同时越限。

仅依赖标准 `hysteria2://` 分享链接时，无法可靠识别物理设备。来源 IP 会受到 NAT、移动网络切换、IPv6 隐私地址和重连影响；客户端自报的任意“设备 ID”又可被非受控客户端伪造。若未来需要真正按硬件授权，必须使用自有受控客户端、每设备独立凭据和服务端设备注册/吊销表，这会改变目前“一条通用节点链接”的使用方式，不能在不更换已发放链接的前提下无感加入。

## 线路与出口实测

测量端为同区域第三台服务器 `203.0.113.20`。该结果能证明两台目标服务器的 Hysteria 握手、UDP 可用性、代理出口和服务器间基础质量，但不代表中国各运营商、Wi-Fi/蜂窝和晚高峰的最后一公里表现。

| 测试 | 203.0.113.10 | 203.0.113.11 |
|---|---:|---:|
| TCP 19999 兼容探测 | 20/20，约 5 ms | 20/20，约 5–6 ms |
| Google `generate_204` | HTTP 204，总 39.2 ms | HTTP 204，总 53.7 ms |
| YouTube 首页 | HTTP 200，总 342.1 ms | HTTP 200，总 412.4 ms |
| Cloudflare 10 MiB | 约 154.4 Mbps | 约 172.9 Mbps |

TCP 19999 只是兼容 Shadowrocket/SSRVPN 的 TCP 延迟测试，不代表 Hysteria 的 UDP/QUIC 数据面。本报告同时完成真实 Hysteria 握手和代理后 HTTP/YouTube 测试，因此没有把 TCP 探测结果冒充节点健康。

公开 DNS-over-HTTPS 从 Cloudflare 和 Google 均返回 `vpn.example.com` 的两个 A 记录：`203.0.113.10` 与 `203.0.113.11`，TTL 60 秒。本机普通 `dig` 受代理 Fake-IP 影响返回 `198.18.*`，该地址不是公网 DNS 记录。

双 A 记录能让新建连接在两台主机之间由 DNS/客户端选择，但不是带健康检查的负载均衡，也不会同步两台 SQLite 的在线数、流量配额、禁用和用户编辑状态。当前两台由同一备份恢复，旧链接可以连接任一台；后续用户管理变更仍需同步到每台服务器，或建设中心认证/计量服务。

## 建议

1. 保持当前 BBR standard。Brutal 依赖准确且稳定的带宽值，多用户共享和线路波动时容易过量发包；当前两台实测无需切换。
2. 不为当前节点启用端口跳跃、obfs 或 Mimic。这些功能需要服务端和客户端成对配置，已发放链接没有相应参数；当前 UDP/QUIC 已健康。
3. 为 `vpn.example.com` 增加外部 UDP/Hysteria 健康检查。若需要故障节点自动摘除，使用带健康检查的 DNS/负载均衡服务，而不是只依赖两个静态 A 记录。
4. 面板虽有登录锁定、会话、CSRF 和固定 sudo 命令，HTTP 仍会明文传输管理员凭据和备份 ZIP。建议仅通过可信管理网络访问，并在云安全组限制 TCP 19998 的来源；不要开放给所有代理用户。
5. 为 TLS 证书建立到期前 180/90/30 天外部告警。证书期内保持证书与私钥不变；到期统一换证时再安排一次链接重新发放。
