# Hysteria2-panel v0.21.1 最终正式版审查报告

审查日期：2026-08-22（Asia/Shanghai）

审查基线：`main = origin/main = v0.21.1 = 7e79f11759936009adfd91ba05e6cfa705c5674f`
仓库状态：审查开始与结束时本地代码基线干净；审查报告是本轮唯一新增文件。

## 结论

当前项目不是“屎山”，而是一个安全控制、事务恢复和测试基础明显高于同类一键面板的功能型单体。既有节点可以继续运行，不需要因为本报告回滚 `v0.21.1`；已部署四节点此前的真实 Hysteria 握手、代理 HTTP 204、服务状态和身份连续性也不因本轮只读审查发生变化。

但 `v0.21.1` 仍不适合作为“以后不用再动的最终封板版”。本轮确认 3 类 P1：首次安装没有跨断电事务恢复；公网登录与内部 Hysteria 认证的容量模型可被并发压垮；发布门禁没有强制完整安装 E2E，且 Release 先公开后签名。另有若干 P2 集中在流量幂等账本、大备份资源合同、防火墙生命周期、兼容性证据和健康闭环。

正式结论：**生产可用，最终封板暂缓；综合评分 79/100。** 修复 3 类 P1、资源安全相关 P2，并取得仓库恢复公开后的完整平台矩阵绿灯后，项目具备进入 90 分以上正式版的基础。

本评分不因以下已确认产品边界扣分：

- 管理面板暂定使用公网 `IP:端口` 的 HTTP，不部署面板 HTTPS；
- Hysteria 节点使用 10 年自签名证书和叶子证书 `pinSHA256`，升级期间不自动换证；
- 流量统计不可用时认证 fail-closed；
- `EGRESS_POLICY=full` 允许完整公网代理能力，但仍拒绝本地、私网、链路本地和特殊用途目标。

HTTP 面板的剩余风险仍需由强密码、固定管理来源安全组以及不可信链路上的 SSH/VPN 管理通道承担，尤其是备份上传和下载；这是已接受风险，不是本轮缺陷。

## 最需要先修复的问题

### [P1] 首次安装不是跨 SIGKILL／断电的一致事务

证据：`install.sh:3032-3037, 3615-3687`、`install.sh:1187-1252`、`tests/installer_e2e.sh:63-92`。

首次部署只写入 `.installing-by-installer`，但标记本身及父目录没有建立明确的 fsync 顺序。安装器随后创建账户和文件、应用 sysctl、启用业务 unit，并在 `install.sh:3649` 启动面板与 Hysteria；直到健康检查、防火墙写入完成后的 `3677-3683` 才写 managed marker、删除 fresh marker并提交，而且提交标记之间同样没有持久化顺序。

现有 `hysteria2-panel-upgrade-recover.service` 只在 `.upgrade-active` 存在时工作，不识别 fresh marker。若安装期间被 `SIGKILL` 或主机断电：

- 已 enable 的业务 unit 可在重启后直接启动未提交部署；
- UFW/firewalld 新增规则只记录在当前 shell 数组中，进程消失后无法撤销；
- fresh 清理删除 sysctl 文件，但不能恢复已写入内核的旧运行时值；
- 只有再次运行同版本安装器才会进入清理；fresh marker 还要求版本字符串等于当前安装器，因此 `v0.21.1` 中断后直接使用 `v0.21.2` 可能拒绝收口。

已有安装的升级事务做得很好：备份清单、fsync、`.upgrade-active`、boot recovery 和 SIGKILL E2E 都已存在；缺口只在首次部署路径，但它与 README 中“不会留下半完成部署”的承诺冲突。

建议：在第一次持久修改前写入并 fsync root-only fresh 事务日志和开机恢复门禁，记录原 sysctl、unit enable 状态及安装器实际新增的每条防火墙规则；业务 unit 不得在 boot recovery 收口前启动。补充在 marker、每条防火墙规则、unit enable、服务 start、健康检查和 commit 前后的 `SIGKILL + reboot` E2E，并验证规则、sysctl、账户、文件和 unit 状态全部回到完整旧状态或完整新状态。

### [P1] 公网登录和内部 Hysteria 认证共享的容量模型会拒绝合法节点

证据：`hysteria2_panel.py:61-64, 1087-1149, 1694-1776, 1820-1908, 1964-1968, 2805-2812, 3237-3256, 3473-3507, 3820-3987`；`install.sh:3210-3236`。

这里有两个会互相放大的触发面：

1. 内部认证服务也使用 `BoundedThreadingHTTPServer`。64 个 worker 用满后，`process_request()` 不排队而是直接关闭新连接。每次有效认证又在 `UsageManager` 的单一全局锁内同步执行两个 stats 入口的流量清算、SQLite 幂等落盘和 online 查询。主机或 Hysteria 重启后的重连潮会快速占满 worker。
2. 公网登录按 IP／IPv6 `/64` 限速，但没有全局 KDF 并发上限。不同来源可同时触发 scrypt 或 PBKDF2；64 个分片锁只是避免同来源竞态，不限制全局并发。两个 HTTP server 每个都允许 64 handler，每个活跃请求另建一个 deadline Timer 线程，而 panel unit 只有 `TasksMax=160`、`MemoryMax=256M`。scrypt 当前 `N=2^14,r=8,p=1` 还是高内存 KDF；面板 OOM／task exhaustion 会因 systemd 依赖关系影响 Hysteria 新认证和服务连续性。

独立复现结果：

- 128 个同时开始的有效内部 auth，请求只有 93 个返回 HTTP 200/`ok=true`，其余 35 个为 `RemoteDisconnected` 或 `ConnectionResetError`；
- 64 个映射到不同分片的来源可同时进入 64 次 KDF，实测并发峰值确为 64；
- 这个问题无需未认证公网直接访问 loopback auth。攻击者只需从公网对 Hysteria 发起连接，Hysteria 自身会调用内部认证；合法用户在节点重启时也可自然触发。

建议：

- 为公网登录增加很小的全局 KDF semaphore，以及全局／账号令牌桶；保留现有每 IP 与 IPv6 `/64` 限制；
- 内部 loopback auth 使用独立的有界等待队列或独立进程/cgroup，不能在 worker 满时静默 reset；
- 对 stats 清算和 online 快照做 single-flight／短时新鲜快照复用，只把设备 pending reservation 保持在锁内，继续保证设备数和额度 fail-closed；
- 用单个 deadline 调度器替代每请求一个 Timer，重新按最坏并发核算 `TasksMax` 和 `MemoryMax`；
- 增加 `>64` 并发有效 auth 零 reset、分布式登录压力下内部 auth 可用、设备上限不被绕过的回归，并暴露 worker 饱和、排队、认证延迟、KDF 拒绝数指标。

### [P1] 发布签名可信，但发布门禁不能证明完整安装测试已通过

证据：`.github/workflows/ci.yml:201-230`、`.github/workflows/release-signature.yml:3-75`，以及仓库 active `Protect main` ruleset。

main ruleset 当前要求 `test (3.8)`、`test (3.12)`、`static-analysis`、`managed-firewall-integration`、`systemd-service-semantics` 和 `rhel-firewall-package-contract`，但没有要求 `full-installer-e2e`。因此完整安装 E2E 失败时，只要其余 required contexts 通过，代码仍可进入 main。

发布工作流只在 `release: published` 后运行。它已经正确验证标签提交严格等于 `origin/main`，并用固定 OIDC identity 签名；但 Release 会先成为公开/latest，再附加 `install.sh.sigstore.json`。若签名任务失败，latest Release 仍会存在，在线更新会因签名包缺失而 fail-closed；更严重的是，签名不能替代未被保护规则强制的完整安装测试。

建议：把 `full-installer-e2e` 加入 main required checks；Release 使用 draft／promotion 流程，在所需 CI 和平台矩阵通过后生成并验证签名，最后一步才 publish。发布失败不得留下未签名的 latest。发布门禁应同时验证 main SHA、严格版本、完整安装/升级/崩溃恢复 E2E、签名身份以及匿名下载可用性。

## P2：应在下一正式版处理

### 流量幂等账本只有时间上限，且每次清理全表扫描

`applied_traffic_batches` 在 `hysteria2_panel.py:1240-1243` 没有 `applied_at` 索引；`apply_traffic_batch()` 在 `1568-1598` 每次插入后执行 30 天删除，没有最大条数。认证在检查设备数和额度前就会清算非零流量，因此持有合法节点 token 的用户可以通过持续产生少量流量并重复认证制造新 batch。

独立量化：259,200 行占约 23,986,176 bytes；SQLite 查询计划为 `SCAN applied_traffic_batches`；无匹配 DELETE 中位 26.61 ms。若连续 30 天平均每秒一个非空批次，约为 259 万行，既拖慢认证锁内事务，也可能把数据库推过 128 MiB 备份上限。

修复应包括 `applied_at` 索引、“保留时间 + 最大条数”双上限、分批清理，并确保刚写入且仍可能由 pending journal 重放的 batch 不会被条数裁剪删除。便携备份可排除不参与迁移的旧幂等账本。

### 合法 128 MiB 备份会超过 restore unit 的 384 MiB 内存预算

`hysteria2_panel.py:508-565, 926-1035` 会把 ZIP 中的数据库整体读为 bytes，`apply_archive()` 又持有 payload、写入 incoming DB、`fetchall()` 全部用户，并在校验和原子替换前再次整库读取。`install.sh:3394-3420` 给 restore service 的 `MemoryMax` 为 384 MiB，但接受的数据库上限是 128 MiB。

定向复现使用 127.16 MiB 合法 SQLite/ZIP，fresh child 峰值 RSS 399.23 MiB，已超过部署的 cgroup 上限。也就是说，输入满足应用合同仍可能被 systemd OOM 杀死。

正确修复是 ZIP 条目流式解压、流式 SHA-256、SQLite 游标迭代和文件级原子复制／替换；短期可把允许上限降到 Linux cgroup 实测安全值。单纯提高 `MemoryMax` 不能解决 `fetchall()` 随用户数量增长的问题。

### 30 秒总截止时间与 131 MiB 备份传输合同冲突

`hysteria2_panel.py:1825-1905` 的 request deadline 从 handler 开始即计时，覆盖数据库快照、ZIP 创建、HTTP 上传/下载以及恢复的两轮校验。允许的最大 archive 约 131 MiB，仅传输本身要在 30 秒完成就要求持续超过 36.6 Mbps，未计 SQLite 和压缩开销；较慢但持续传输的可信管理链路会被强制断开。

普通和未认证请求应继续使用 30 秒总截止与 10 秒空闲超时。通过 session、CSRF 和 Content-Length 校验的串行备份维护传输应使用独立的 10 秒 idle timeout，以及按大小计算但有硬上限的 10–15 分钟总期限，并增加慢速大文件与 slowloris 回归。

### 备份自验证、磁盘预算和保留生命周期没有闭环

`BackupManager.create_archive()` 在 `hysteria2_panel.py:442-506` 生成后不立即调用 `validate_archive()`／SQLite integrity；异常时 partial ZIP 没有统一 finally 清理。恢复前没有保守的 free-space 预检，恢复过程中会复制 archive、当前 DB 和 staged DB。安装器只清理时间戳升级备份，`restore-*` 与 `failed-restore-*` 没有“天数 + 数量”保留上限。

建议在允许下载前完成自验证，失败必清 partial；按最坏多副本计算可用空间和固定 headroom；给 restore/quarantine 双重保留上限；暴露最近一次成功备份/恢复和年龄。定时异机备份可作为可选运维功能，但必须同时做 SHA、SQLite integrity 和实际恢复演练，不能只证明“ZIP 被创建”。

### 防火墙没有持久的项目规则所有权，改端口会累积旧放行

`install.sh:2149-2498, 3687` 只根据当前端口构造和新增 UFW/firewalld 规则。项目实际新增的规则只保存在进程内 `FIREWALL_APPLIED`；成功后数组被清空，磁盘没有 managed-firewall 清单。显式修改 Hysteria 或面板端口后，旧端口的 allow 永久残留；SIGKILL 后新增规则同样无法跨进程撤销。

应建立 root-only、逐阶段 fsync 的防火墙 journal，只记录“安装器新增而非用户预先存在”的 manager/zone/scope/rule。新服务和新规则验收成功后，才删除清单中属于项目且不再需要的旧规则；任何情况下都不得删除用户已有规则。该 journal 可与首次安装 crash recovery 共用事务框架。

### 声明支持的系统范围超过真实兼容性证据

`README.md:12` 声明 Debian、Ubuntu、Rocky、Alma、CentOS Stream、Fedora，覆盖 apt/dnf/yum、amd64/arm64。每日完整矩阵在 `.github/workflows/installer-nightly.yml:18-35` 只覆盖 Ubuntu 24.04 和 Rocky 9 两架构；PR 的完整 E2E 只有 Ubuntu，Rocky 容器不能证明宿主 SELinux enforcing，RHEL job 只验证软件包和命令存在。

未发现上述其他发行版已坏，问题是支持合同证据不足。README 应列明“保证支持/定期测试”的最低版本与 best-effort 范围；至少补 Debian stable 两架构，以及 SELinux enforcing 的 RHEL-family 9 VM 上真实 install/upgrade/reboot/firewalld 验证。Alma、CentOS Stream、Fedora可先做包解析和 systemd smoke。

### 健康检查能诊断 crash，但没有完成执行结果和 active-hang 闭环

正向部分：长驻 unit 已 `Restart=on-failure`，`run_supervised_services()` 会把 worker 异常退出升级为整个 panel 进程失败，因此 crash、OOM、SIGKILL 和 reboot 能恢复。

缺口有两类：

- `UsageManager.collect_once()` 在 `/kick` 前已把 stats health 标绿；若禁用、删除或超额用户的 `kick_many()` 单独失败，`/readyz` 仍为 200、failure metric 不增加，现有超额连接可能继续在线；
- unit 都是 `Type=simple`，无 `WatchdogSec`、`OnFailure`、健康 timer 或外部数据面探针。进程 active 但死锁、stats 长期异常、磁盘满、备份陈旧、证书临期和异步操作失败都不会主动告警。

最低限度应为 enforcement/kick 增加独立最近成功状态和失败计数；panel supervisor 可用 stdlib `NOTIFY_SOCKET` 实现 `Type=notify + WatchdogSec`；独立 timer 连续 N 次 loopback 失败时告警。Hysteria 应由外部真实 QUIC/代理 HTTP 204 探针验证，外网源站失败不能直接触发盲重启。补充低基数的 worker 饱和、HTTP RED、DB/WAL/磁盘、backup age、cert days、pending journal、update/restore outcome 指标。

### 核心责任仍过度集中，未来修改成本偏高

`hysteria2_panel.py` 有 4,831 行，`install.sh` 有 3,719 行。知识图谱测得：

- `run_supervised_services`：cyclomatic 31、cognitive 103；
- `configure_firewall`：cyclomatic 31、cognitive 82；
- `UsageManager._persist_pending_traffic_locked`：cognitive 62；
- `main`：cognitive 60；
- `PanelHandler._handle_user_action`：cognitive 58；
- `_dashboard`：360 行。

这不是“文件大就等于屎山”：关键输入有界、SQL 参数化、事务和测试都比较扎实，而且 `hy2panel/operations.py`、`health.py`、`release.py` 已形成模块缝隙。问题是备份、数据库、HTTP、统计、supervisor 和 CLI 仍共享一个修改面，安装器的防火墙/事务逻辑也难以局部证明。

建议不重写、不引入 Web 框架。按 `storage.py`、`usage.py`、`backup_restore.py`、`http/handlers.py` 和 installer 的 transaction/firewall library 一次迁移一个边界，保留原导入兼容层；每次只做行为等价拆分并跑现有测试。先修 P1，再重构，避免在缺陷修复中同时大搬家。

### 已安装二进制可安全复用，却被每次重复下载

README bootstrap 先下载 Cosign；安装器随后又下载同一版本。在线更新已经使用 `/opt/hysteria2-panel/bin/cosign` 验证新安装器，进入安装器后仍重新下载 Cosign 和 Hysteria。

当前官方资产大小：Cosign amd64 141,178,250 bytes、arm64 132,747,403 bytes；Hysteria amd64 23,199,906 bytes、arm64 21,430,434 bytes。nightly 每个矩阵执行安装器三次，一轮四平台全绿仅 Cosign 下载约 1.64 GB。它既拖慢小带宽节点，也扩大 GitHub/CDN 短暂抖动的失败面。

安装器可先把 root-owned 已安装 binary 复制到 staging，再按新安装器内的固定 SHA-256 重新验证；只有缺失或哈希不符才下载。bootstrap 的用户临时文件不能直接信任，也必须进入 root-owned staging 后重哈希。

## P3：可排入后续维护

### 证书生命周期只有身份连续性，没有到期可观测性

当前 10 年自签名证书和 leaf pin 不自动轮换是合理设计。盲目自动续签会改变 `pinSHA256`，令旧 URI 失效；面板暂定 HTTP，也不需要为了面板引入 ACME。

现有证书 `notAfter` 只在备份/恢复时解析。建议复用该逻辑，在 dashboard 和 Prometheus 暴露 expiry timestamp／days，按 180/90/30 天告警但不自动替换、不令 readiness 失败；补充维护窗口、临时第二入口、生成新 URI、分批重分享和旧入口退役的正式 runbook。若未来新增 ACME，应是显式的域名模式，而不是当前 IP/self-signed 模式的静默变化。

### Dashboard 当前可用，但全量渲染有明确规模上限

356 用户定向测试得到约 966 KB 未压缩 HTML、32.5 KB gzip，本地生成约 25 ms；当前约 351 用户不是性能阻断，也没有 N+1 SQL。问题是页面全量读取、排序，并为每个用户生成多个表单，DOM 成本会线性增长。

当用户规模超过约 500–1000 或浏览器 profile 超过预算时，引入 50/100 条服务端分页；汇总和 Top 5 用 SQL 聚合保留。现在无需前端框架或虚拟列表重写。

### 审计事件有少量“成功语义提前记录”

`hysteria2_panel.py:2742-2797` 在文件实际发送完成前记录 `backup_downloaded`，并在 restore controller 真正 queue 成功前记录 `restore_queued`。断流或 queue 失败会留下成功型事件；update/restore 也缺最终结果与发起者的关联。

建议改为 `backup_generated/download_started`，queue 成功后再记 queued；root oneshot 持久化 operation id、actor、最终 success/failure 和失败阶段。审计日志仍保留现有 90 天 + 10,000 行双上限。

当前仍缺“恢复公开之后，同一 SHA 的全矩阵绿色 run”。本轮是只读审查，没有主动 dispatch GitHub workflow。下一次正式发布前应手工重跑，并增加失败通知、匿名 release/raw/API synthetic probe；更稳妥的长期方案是把受签名保护的 Release 做成自包含应用 payload，减少对仓库 visibility 与 raw GitHub 的可用性耦合。

## 系统、节点与网络优化结论

现有默认值总体合理，不建议继续堆“万能 sysctl”：

- Hysteria 使用官方 `bbr`、`standard` profile，并忽略客户端误报带宽；
- Linux UDP 收发缓冲至少 16 MiB，符合 [Hysteria 性能指南](https://v2.hysteria.network/docs/advanced/Performance/)；已有更高值不会被降低；
- Hysteria unit 使用 `Nice=-5`、`LimitNOFILE=1048576`；
- 仅在内核支持时启用服务器 TCP 出站 `fq + bbr`，不支持则安全跳过；
- 未启用未经线路测量证明的 Brutal、RPS、固定 MTU、端口跳跃或激进 qdisc；
- `full` ACL 仍先拒绝本地和特殊地址，不能通过代理访问主机 loopback／内网；它与面板公网暴露是两个不同边界。

没有代码证据表明当前四节点需要额外内核调优。后续性能优化应先以 CPU、NIC、QUIC 重传、RTT/丢包和真实代理吞吐 profile 为依据，避免把参数数量当作速度。

## 供应链与依赖结论

正向控制较强：

- Python 运行时只使用标准库，二维码实现为固定 vendored 文件，不存在运行时 pip 依赖漂移；
- Hysteria `2.12.1` 与 Cosign `3.1.3` 版本和双架构 SHA-256 固定；
- GitHub Actions 使用完整 commit SHA；
- Release signer 校验标签提交严格等于受保护 main、版本严格匹配，并固定 Sigstore issuer 和 exact workflow/tag identity；
- 在线更新限制响应体大小、安装器头、严格 semver、shell 语法、固定 PATH 和 root-owned Cosign；签名不匹配时 fail-closed；
- Release `v0.21.1` 的 `install.sh` 与 Sigstore bundle 已按公开资产重新下载并匹配预期 SHA-256。

需要修的不是“加更多依赖”，而是发布门禁、分发自包含性和已验证二进制复用。

## 修复顺序

### 第一阶段：正式版阻断项

1. 关闭发布门禁缺口：required `full-installer-e2e`，签名后再 publish，并取得 PUBLIC 恢复后的四平台绿灯。
2. 修复认证容量：全局 KDF 并发、auth 有界队列／独立资源、stats single-flight、压力指标与并发回归。
3. 为首次安装建立持久 fresh journal、boot recovery/gate 和逐阶段 SIGKILL+reboot E2E。

### 第二阶段：资源与生命周期

4. 为 `applied_traffic_batches` 加索引和条数上限，减少认证热路径的重复 stats 清算。
5. 把 restore 改为流式，修复 128 MiB／384 MiB 合同；拆分维护传输 deadline。
6. 补备份自验证、磁盘预检、restore/quarantine 保留上限和 managed-firewall journal。

### 第三阶段：长期正式化

7. 补 enforcement 健康、watchdog、外部 QUIC/HTTP 204、证书和备份年龄告警。
8. 明确发行版支持等级并扩展 Debian/SELinux VM 证据。
9. 复用已验证二进制，并逐模块拆分 Python 与 installer 热点；不要同时重写 UI 或引入新框架。

每阶段应单独合并并完整回归，不建议把事务、认证、备份和重构一次性塞进一个大版本。
