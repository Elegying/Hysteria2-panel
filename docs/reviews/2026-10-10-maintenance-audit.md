## P1：维护任务留下的新批次被面板旧缓存跳过或删除

实际调用链为 `apply-egress-policy` → 维护锁与认证门禁 → 独立采集排他锁 → `settle_egress_traffic` → `sync_traffic`。出站切换必须先排空和结算，运行中的面板进程不退出。维护任务创建新的 `UsageManager`，与面板共用 `pending-traffic.json`，但面板原先只在构造时加载一次日志。

复现使用真实 SQLite、真实待入账文件、真实 `flock` 和 Python CLI 入口，注入维护批次提交失败：

1. 面板持有尚未提交的 100 字节批次 A。
2. 维护任务先成功提交 A，再采样 200 字节并写成批次 B；提交 B 失败，策略切换中止，B 留在磁盘上。
3. 面板继续运行，幂等重试内存中的 A 后，无条件删除了当前磁盘上的 B。
4. 面板再采样 50 字节，最终只有 150 字节入账，正确总量应为 350 字节。

面板内存为空时同样受影响：它未重新加载维护留下的 200 字节批次，直接用 50 字节的新采样覆盖日志，最终只有 50 字节而不是 250 字节。此路径不要求面板之前发生故障。

测试在维护采样期间尝试进入面板共享采集锁，确认排他锁确实阻止采集。因此根因是串行交接后的缓存失效，现有互斥锁不能单独消除这个问题。维护日志原有的 `0600` 权限及数据库所有者继承正确，本轮没有把它误判成权限缺陷。

## 修复

- 复用原有日志校验，提取读取入口；每次清空内存批次后重新读取磁盘，先重放维护留下的批次。
- 删除日志前核对批次编号，只删除与当前已处理批次一致的文件，保留其他批次。
- 重放、校验或清理失败时，在读取并清零新的内核统计之前结束本次采集，保留恢复依据。
- 继续使用原有 SQLite 批次幂等性、采样时间、月初重置和域名记账规则；已提交后清理前重启不会重复累计。

修复集中在 `UsageManager` 的日志读、清理和重放边界，没有新增协议、数据库表或常驻进程。安装器面板 SHA-256 已同步。交接约定记录于 [ADR 025](../decisions/ADR-025-maintenance-journal-handoff.md)，架构、运维、变更日志与功能验收 OPS-06 已同步。

## 回归与继续复审

[新增回归](../../tests/test_maintenance_journal_handoff.py)共 6 项，在修复前均失败，修复后均通过：

| 场景 | 核对结果 |
| --- | --- |
| 面板内存为空，维护留下新日志 | 200 + 50 = 250，日志正常清理 |
| 面板保留旧批次，维护写入新批次 | 100 + 200 + 50 = 350，旧域名记录只记一次 |
| 面板旧批次已提交但未清理 | 旧批次幂等重试，不重复记账 |
| 接管新批次时数据库继续失败 | 新日志字节保持一致，50 字节统计尚未读取；故障恢复后总量为 350 |
| 接管批次提交后、清理前重启 | 新采集器重放不重复计量，总量为 250 |
| 存活面板遇到新出现的损坏日志 | 保留原文件，在清零新统计前失败 |

进一步检查确认：

- 安装和恢复流程先停止面板写入，再进行最终结算；没有把手工并行运行未协调的 `sync-traffic` 当作支持路径。
- 出站维护仍只选择处于 active 的统计入口，状态不稳定时中止；结算失败时不会进入策略写入。
- 服务停止、重启与网页手动备份继续通过面板同一 `UsageManager` 结算；此次交接修改没有移除原有排空或互斥步骤。
- 普通出站切换异常继续尝试恢复原配置和原服务状态；中断事务沿用持久恢复记录。已停止入口的处理及异常回滚控制结构未改动。
- 上轮异地备份使用已提交快照的决定保持有效，不重新引入额外清零采集器。

这些路径没有新增确认其他缺陷；这不代表所有部署组合都已经通过真实运行验收。
