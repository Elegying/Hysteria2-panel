## 总体判断

有明显的单体膨胀、业务/视图耦合和重复维护问题，但不是所有长文件都应立即拆掉。流量账本、节点签名协议、升级回滚中的复杂性有实际约束和回归测试；不能为缩短代码删除它们。当前优先修复共享逻辑边界和打包漂移，数据库迁移、认证、结算状态机应分阶段拆分。

## 本轮完成的代码整理

1. `machine_forecasts` 移到预算模块，网页保留原导入名兼容调用，移动端直接使用预算模块。
2. `server_monitor_payload`、`line_monitor_payload` 统一网页与移动监控数据，HTTP 层仅负责认证、响应包装与错误转换。检测读取绝不触发探测。
3. 新增 `GET /api/v1/mobile/server-monitor` 和 `GET /api/v1/mobile/line-monitor?range=5m|today`；capabilities 发布精确的只读能力，不宣称支持远端重启写操作。
4. 运维状态排序增加同秒 rowid 决胜，避免最近命令时间相同时取到旧记录；范围参数拒绝多值歧义。
5. 排空拒绝使用独立异常和稳定错误码，网页区分“取消操作、服务保持运行”与一般执行失败；有指令 ACK 回归，异常细节不返回客户端。
6. 安装源码哈希检查/同步工具和 CI 门禁，新增模块遗漏、缺哈希、只读检查、二进制哈希不被修改均有测试。

## 一键部署能力

安装源码包含当前界面、资源监控、移动 API 所需 Python 模块；安装目录及编译步骤齐全，源码 SHA-256 与当前工作区一致。短入口仍承担系统检查、依赖引导、固定版本下载和 Sigstore 验证，真正安装工作由安装器完成。用户粘贴代码短，不意味着删除安装恢复逻辑。

**现在不能承诺公开一键命令部署出本工作区的全部功能。** 原因不是缺了某个网页文件，而是源码/标签/签名 Release 尚未形成一致的发布物。当前线上是此前源码更新，不是本轮修改后的新发布。

正式可交付的验收顺序：

1. 完成当前源码提交，使用新的版本号，更新 bootstrap/安装器/版本文件及相关文档；执行 `python3 ops/source_manifest.py --write` 后再只读检查。
2. CI 验证全部源码、固定二进制、签名流程；从同一固定提交生成 Release，不移动已有标签。
3. 在一次性 systemd Linux 上运行 `tests/installer_e2e.sh` 和对接 E2E，覆盖首次安装、升级、失败回滚、HTTPS、节点注册和真实 QUIC 出网。
4. 验证公开短入口能取得对应 install.sh、sigstore bundle、两种架构二进制；从干净机器执行，再验收网页和移动能力。

本轮 Linux 测试在独立目录、非特权用户下运行，**未在生产机器执行全新安装器**。已有服务器升级成功不能替代干净机器的一键安装验收。

## 节点对接能力

已具备类型/地区/域名/跳跃参数、短时注册令牌、节点签名、协议初始化、身份校验、数据面安装与真实连接检测、中央鉴权/账本/指令、断连和撤销流程。Agent 独立部署，部分采样逻辑与面板相似属于部署边界约束，不宜直接强行导入面板完整包。

仍有边界：DNS 由管理员设置；网络封锁不能靠对接成功判断；旧 Agent 缺能力需要升级；重启在未排空连接时可能拒绝；远端全局改端口/跳跃与修改订阅下发值不是同一功能。移动端写接口也未覆盖全部网页运维操作。

## Android 接口结论

现有客户端已使用的路由有服务端支持，新增网页能力并未全部进入 App。详见 [Android 改版接口准备情况](ANDROID_API_READINESS.md)。本轮补的是监控只读基础，未把网页的 cookie/CSRF 接口直接暴露给 Bearer 客户端。

后续顺序建议：先统一数据模型与速率口径 → 重做总览/节点只读页 → 增加受控运维写接口 → 备份恢复/面板更新 → 真机弱网、账号切换、签名覆盖安装验收。
