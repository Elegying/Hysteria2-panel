# ADR-011：使用双 Hysteria 进程实现单账号 UDP 443 授权

## 状态

已接受

## 日期

2026-08-12

## 背景

主 Hysteria 服务继续监听 UDP `19999`，但部分账号需要额外使用 UDP `443`，且未授权账号不能通过 `443` 连接。现有 token、TLS 证书指纹和已分享 URI 必须保持有效。

Hysteria 服务端配置的 `listen` 是单个监听地址。官方 HTTP 认证回调只提供客户端地址、认证字符串和发送字节数，不包含服务端收到连接的目标端口。因此一个 Hysteria 进程无法在认证阶段判断连接来自 `19999` 还是 `443`。

## 决策

保留主 Hysteria 进程和 `/auth` 回调不变，新增第二个只监听 UDP `443` 的 Hysteria 进程。第二进程使用相同证书、统计密钥和 ACL，但调用独立的 `/auth/udp-443` 路径，并使用独立的本机统计监听端口 `19995`。

代理用户表增加默认值为假的 `allow_udp_443` 字段。`/auth/udp-443` 只认证已启用且该字段为真的账号；主 `/auth` 不检查该字段。面板把两个 Hysteria 进程的 `/traffic` 和 `/online` 结果按用户名相加，统一执行原有设备数、流量额度、断开和重置逻辑。

第二进程由 `hysteria2-panel-server-443.service` 管理，并通过 `Wants` 与 `PartOf` 跟随主 Hysteria 服务启停和重启。服务继续以非 root 的 `hy2server` 运行，仅通过 systemd 获得绑定特权端口所需的 `CAP_NET_BIND_SERVICE`。安装器把配置、服务单元、端口占用、健康检查、升级备份和失败回滚作为同一个部署事务处理。

## 考虑过的替代方案

### 在一个监听器中使用端口范围或端口跳跃

这可以让同一个进程接收多个端口，但认证回调仍不知道目标端口，结果是所有有效账号都能使用 UDP `443`，无法满足账号级授权。

### 把 UDP 443 转发到 UDP 19999

DNAT 或端口转发同样会在认证前丢失入口区分，所有账号共享同一认证策略，也无法单独统计两个入口。

### 为每个获准账号启动一个 Hysteria 进程

每个账号需要独立端口或地址，不能共同绑定 UDP `443`，服务数量和运维成本也随用户线性增长。

## 后果

- 获准账号只需把客户端服务器端口改为 `443`；原 `19999` 配置继续有效。
- 未获准账号在 UDP `443` 入口认证失败；旧数据库和旧备份迁移后默认不获准。
- 两个入口共用 token、TLS 身份、设备数和流量额度，不生成第二套用户凭据。
- 服务器多运行一个 Hysteria 进程并占用一个本机统计端口；任一统计入口不可用时，已成功读取并清零的其他入口流量仍先持久化，新认证随后按原有安全策略失败关闭，避免丢失流量或绕过合并限额。
- UDP `443` 必须没有被其他 UDP 服务占用，并需要管理员在云安全组或主机防火墙中放行；安装器不会自行修改防火墙。
