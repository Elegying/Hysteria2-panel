# ADR 027：本机累计计量与只读展示

- 状态：已实现，待真实 Linux 部署验收
- 日期：2026-10-22

## 问题

本机 `/traffic?clear=1` 清零后到持久化之间存在不可恢复窗口。普通网页和 App 查询还会同步触发采集、结算和写盘，概览对用户、节点及服务状态存在重复查询。

已核对项目固定版本的 [Hysteria 2.12.1 统计接口实现](https://github.com/apernet/hysteria/blob/app/v2.12.1/extras/trafficlogger/http.go)：不带 `clear` 的读取保留累计计数，主动清零会替换内存计数表。

## 决定

1. 正常生产工厂给每个统计客户端绑定固定的本机 systemd 单元。采样前后读取 `InvocationID` 并验证一致；使用非清零 `/traffic`，同周期计算差值，新周期从零计算。同周期计数减少、响应超限、周期无法确认时保留原检查点并报错。
2. 独立的 `local-traffic.cumulative.json` 同时保存两个入口的累计检查点和至多一个待入账批次。顺序是原子写入并同步日志、按稳定 ID 通过已有 SQLite 事务入账、原子标记批次完成。进程可在任一步重启，已提交但尚未标记完成的批次依靠既有去重重放。
3. 沿用进程锁和跨进程采集锁；每次采集重新读取文件，避免存活面板的旧内存覆盖维护助手的新状态。文件只允许普通、单硬链接、数据库所有者、`0600`，读取及写入大小均有界。不修改数据库或便携备份格式。
4. 先重放旧版 `pending-traffic.json` 和累计日志，再进行新采样。域名聚合沿用已有有界日志及采样时间规则，独立于累计字节基线。部分入口故障仍持久化健康入口，随后报告整体采集失败；新认证保持失败关闭。
5. 安装器在预检和最终切换前探测备份中旧面板的 `accounting-mode`。仅旧解析器明确返回状态 2 时向新维护助手传入 `--legacy-traffic`；未知模式或其他错误均停止升级。回滚先由新助手结算并停止所有相关内核，再恢复旧代码，不能让旧清零采集器直接接管仍在运行的累计内核。
6. `UsageManager.snapshot()` 只读已提交账本和当前在线状态，不再调用结算。后台、认证、手工备份、用量调整及服务维护继续使用原强制结算边界。最近本机采集失败、尚无成功采样或超过 30 秒时展示不可用，并保留采样时间。
7. 同一概览复用用户、节点、在线源记录和服务状态；在线源数据按各调用者的既有阈值重新投影，保留管理端 150 秒与认证 43 秒的区别。用户配置不做整页缓存，权限变更和新增删除立即可读。旧客户端继续使用原字段，新增采样时间字段可忽略。

## 边界

- 累计检查点属于本机运行状态，不随便携备份迁移；恢复流程会先结算并停止内核，新运行周期从新基线开始。
- 累计状态包含当前内核周期出现过的账号；响应或日志达到容量上限后需受管维护，不能删除检查点或手工清零来绕过。
- 内核或整机被强杀前尚未采样的计数仍可能丢失；旧版升级切换前继续保留原有清零计量窗口。
- 展示流量通常滞后不超过一个后台采集周期，默认约 10 秒。响应生成时间与采样时间分别表达，不承诺每次页面刷新均触发持久化。

## 验证

回归使用真实回环 HTTP、SQLite、文件和子进程退出，覆盖首次写日志前、落盘后、数据库提交后中断，双入口、独立重启、部分故障、写盘失败、旧日志接管、维护交接和旧版切换。展示回归检查重复查询次数、无采集或 fsync 副作用、用户变更可见性以及管理/认证阈值。完整 Python、Flutter 与静态检查结果另随交付记录；这些自动化不代替 Linux systemd、真实 Hysteria 数据面和 Android 真机验收。
