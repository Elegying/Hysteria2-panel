# ADR-013：无密钥签名更新、模块边界与运行时就绪

日期：2026-08-17
状态：已接受

## 背景

固定仓库和严格版本号只能限制下载位置，不能证明下载到的安装器由本项目发布。主程序持续增长也提高了审查和冲突成本；单一 `/healthz` 只能证明 HTTP 进程回应，无法证明数据库、认证和统计链路可用。

维护者明确不希望在本地保存、备份或轮换长期发布私钥。

## 决策

1. 正式发布只允许从目标 `vX.Y.Z` 标签引用显式调度专用工作流。工作流签名前重新拉取受保护的 `origin/main`，要求标签提交与当前主分支提交完全一致，并核对全部必需 CI check-runs（包括完整安装器 E2E）。同名 Release 不存在时先创建草稿；已存在时必须仍为非 prerelease 的草稿。
2. 更新器固定证书身份为本仓库、该工作流和目标标签，并固定 OIDC issuer。验签先于 shell 语法检查和任何执行；bundle 缺失、身份不匹配、内容被修改或 Cosign 不可用均安全停止。
3. 工作流使用 GitHub Actions OIDC 与 Sigstore/Cosign 对 `install.sh` 执行无密钥 blob 签名，把安装器和 `install.sh.sigstore.json` 上传到草稿 Release，再重新下载、逐字节比较并复核签名。只有这些检查全部通过后，最后一步才把草稿公开；已公开的 Release 不允许进入该流程。
4. 安装器固定 Cosign 版本与 amd64/arm64 SHA-256，将其作为受管运行时工具安装。发布流程不保存私钥，也不使用仓库 secret 保存签名密钥。
5. 主程序先拆出低耦合边界：版本、网页静态资源、固定运维控制、发布更新和健康状态。数据库、认证、流量策略与 HTTP 编排暂留主文件，避免一次迁移过大。
6. `/healthz` 只表示存活；`/readyz` 聚合数据库、关键工作线程和最近完整统计同步；`/metrics` 只允许回环来源并使用无用户标签的固定指标集合。

## 后果

- 维护者无需持有本地签名文件，签名身份与可审计的 GitHub 工作流绑定。
- 公开 Release 不再短暂暴露未签名安装器；任何失败都停留在草稿阶段。调度必须使用目标标签作为 `--ref`，否则签名身份不符合更新器固定值并被工作流提前拒绝。
- 本地测试能证明发布门禁引用完整安装器 E2E，但 `Protect main` ruleset 仍是 GitHub 远端配置，必须在推送后单独设置并回读确认。
- 首次从未实现签名验证的旧版本升级，仍受旧更新器的信任边界限制；完成一次受控升级后，后续在线更新才具备连续的签名校验链。
- 每台服务器增加约 130–145 MB 的 Cosign 可执行文件，并在在线验证时依赖 Sigstore 公共透明日志/证书链可用性。
- 模块数和安装器校验项增加，但边界更清晰，后续可在保持接口测试的前提下继续拆分存储与 HTTP 层。
- readiness 可能在统计端点暂时故障时返回 503，即使 HTTP 页面仍能打开；这是有意区分“活着”和“可安全提供完整服务”。
